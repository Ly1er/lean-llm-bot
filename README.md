# 把聊天机器人成本砍掉 90%：三段式 Prompt + 前缀缓存实战

> 同一套模型、同一个机器人，只改 Prompt 的组织方式，单请求成本从 **0.0096 元** 降到 **0.00086 元**。
> 不是压缩模型，而是让每一轮请求里「不该重发的东西」不再重发。

**本项目使用 DeepSeek Harness 构建，开发过程由 DeepSeek V4.1 Flash 辅助。**

> 非官方项目：与 DeepSeek 及其关联公司、腾讯及其关联公司均无隶属、合作或背书关系。

## 1. 实测数据

两次都是 DeepSeek `deepseek-flash`，口径来自平台账单（单价：缓存命中 0.02 元/百万、未命中 1 元/百万、输出 4 元/百万）。

| | V1（旧结构） | V2（三段式） |
|---|---|---|
| 日期 | 11-01 | 11-07 |
| 请求数 | 533 | 38 |
| 总 token | 13,951,106 | 271,702 |
| 缓存命中率 | 79.1% | 93.4% |
| 总花费 | 5.115342 元 | 0.032774 元 |
| **单请求成本** | **0.0096 元** | **0.00086 元** |

单请求成本下降 **91%**；稳态对话（排除首轮）命中率 96–98%，每轮新增输入从 ~1050 token 降到 ~114 token。

## 2. 为什么 V1 那么贵

旧版把三样东西塞进**每一条**用户消息：人设（400+ 字）、记忆文件末尾 1000 字、群里最近 8 条上下文。
于是每轮新消息 1600+ 字——这部分**天然不可缓存**。

前缀缓存只认「从头开始逐字节相同」的前缀，新消息永远在最末尾，一条也省不掉。
实测归因（`examples/dsh_report_cache.py`）：未命中 token ≈ 新消息长度 + 运行时上下文，
和 64 token 对齐误差几十个，说明**没有前缀断裂**，纯粹是「每轮带太多新内容」。

## 3. 三段式 Prompt

```
┌─────────────────────────────────────┐
│ ① 静态段：人设 + 记忆快照 + 当天流水   │  每个会话只发一次，之后字节级不变
├─────────────────────────────────────┤
│ ② 历史段：所有后续消息                  │  只追加，永不改写
├─────────────────────────────────────┤
│ ③ 动态块：本轮新信息（≤5% token）       │  每轮变化，但在最末尾
└─────────────────────────────────────┘
```

约束：

- 静态段 = 会话第一条消息，**只投一次**；记忆变了就追加「记忆更新」，绝不重写历史
- 所有会变的内容（情绪、作息、话题栈）统一走动态块预算管理器，超预算按优先级丢弃
- 静态段的变更检测只比「稳定内容」的 hash，**不要把每天增长的流水算进 hash**

## 5. 快速开始（零配置）

不需要 API Key，clone 下来直接跑：

```bash
node demo.js      # 或 npm run demo
```

你会看到：

1. 静态段全文（人设 + 记忆 + 当天流水），以及它只出现一次
2. 六轮对话里每轮的 body token（20–30）
3. 模拟缓存账：turn2 起命中率 94–97%，V2 与 V1 的六轮成本对比
4. 动态块预算：预算压到 12 token 时，低优先级的「情绪」被丢弃

跑单测：

```bash
npm test          # Node >= 22
```

接入自己的项目：

```js
import { PromptBuilder } from './lib/prompt-builder.js';

const b = new PromptBuilder({ cwd: './data', persona: '你是……', memMarkers: true, maxDynamicTokens: 120 });

// 会话第一条
const first = b.bootstrapMessage({ diaryChars: 650 }) + '\n\n' + b.turnMessage({ header: '用户说：你好' });

// 之后每轮
const next = b.turnMessage({ header: '用户说：今天好累' });

// 记忆变化时（返回 null 表示没变）
const update = b.memoryUpdateMessage();
```

## 6. 记忆写入通道

模型在回复末尾输出：

```
<mem section="长期" type="事实" importance="0.9">用户A 的生日是 3 月 5 日</mem>
```

- 插件侧解析并剥离，**用户永远看不到标记**
- 条目先进 `memory/pending.jsonl`（只追加）
- 每天凌晨合并进 `MEMORY.md`：去重、好感度按 ID 覆盖、写前备份、原子写、归档
- 白天只写 pending，`MEMORY.md` 一天只动一次

## 7. 成本账本与看门狗

- `usage_ledger.py --write`：按天结算到 `usage_daily.jsonl`，一天一行、同日期覆盖
- `cost_guard.py`：当日 = 账本已结算 + `settled_until` 之后的增量
  - `settled_until` 防重复：同一天先写账本、后来有新请求只补差额
  - 会话被清理后增量归零，账本兜底

## 8. 踩坑指南

1. **动态内容千万别写进 system / 静态段**
   情绪、作息、话题栈这类每轮都变的，一旦进静态段就等于每轮重投，前缀直接断。
2. **时间戳会导致前缀断裂**
   别把「现在 12:03:47」这种秒级时间放进静态段；要放就放日期，或者塞进动态块。
3. **改静态段文案必须重启**
   代码加载在进程里，改了不重启跑的还是旧逻辑；我们因此多投过一次记忆更新。
4. **流水别进变更 hash**
   当天流水每 5 分钟增长，进了 hash 就等于每轮重投静态段。
5. **清会话要清状态**
   清了会话但没清「已投静态段」标记，新会话不会 bootstrap，机器人直接失忆。
6. **纯文字先到、图片后到**
   会先回一句「图呢」。解决：等待窗口内同群来了带图消息，就跳过这条纯文字。
7. **历史只追加，不要"整理"**
   任何对已发送消息的改写都会让前缀缓存失效；要更新记忆就追加一条更新消息。
